# v0.3 Specification — Plant Builder

## 1. Goal
Let users **build and edit the plant themselves** in the web console, run multi-line plants with shared resources and shifts, import their own 3D meshes, and start from ready-made templates. The server stays the single source of truth: a built plant is applied with `PUT /api/plant`, and every client then gets a fresh `snapshot`.

## 2. Model additions (all optional, so v0.1/v0.2 plants stay valid)
The types are frozen in `Core/Contracts/Plant.cs` and `ui/src/net/contracts.ts`. See `contracts/examples/plant.v03.json`.

- **Lines:** `plant.lines[] = {id,name}` and `asset.lineId`. A line is a labelling group; flows may cross lines. Assets without a `lineId` belong to no line. When `lines` is present, `KpiReport.lines[]` carries per-line KPIs computed over that line's assets. A line's throughput is the good parts counted at its sink(s); a line with no sink uses its last asset in flow order.
- **Resources:** `plant.resources[] = {id,name,kind: operator|agv|tool,count}` and `asset.resourceId`.
  - An asset with a `resourceId` needs one free unit **for the whole cycle**. The unit is acquired when a cycle starts and released when the cycle ends. If none is free, the asset stays `Starved` (waiting, no cycle progress) and the wait time is counted.
  - Fairness is FIFO by wait start, with ties broken by plant asset order.
  - Only machine, robot and inspection assets may reference a resource.
  - `KpiReport.resources[]` reports `utilization` (busy unit-seconds ÷ (count × elapsed)) and `waitSeconds`. The engine exposes cumulative `ResourceStats` through `GetResourceStats()`.
- **Shifts:** `plant.calendar = {startHourOfDay, shifts[]}` and `asset.shiftId`.
  - Sim t=0 is `startHourOfDay` of day 1, and the pattern repeats every 24 h.
  - An asset with a `shiftId` is `Off` outside its shift window, and its in-progress cycle pauses (like maintenance). Off time does not count as planned time in OEE availability.
  - A window with `endHour < startHour` wraps midnight (22→6).
- **Mesh:** `asset.mesh` is a URL such as `/api/meshes/{id}/file`. The viewport loads the glTF/GLB and fits it to the asset's `size` box (centred on x/z, sitting on y=0), keeping the status stack light. Unity falls back to the procedural model.

## 3. Validation (`PlantValidator`, `Core/Validation/PlantValidator.cs`)
Returns a `ValidationResult`. Severity `critical` blocks apply; `warning` does not. Codes are stable strings:

| Code | Severity | Rule |
|---|---|---|
| `EMPTY_PLANT` | critical | no assets |
| `DUPLICATE_ID` | critical | duplicate asset, sensor, line, resource, shift or connection id |
| `BAD_ID` | critical | id is empty or has characters outside `A-Za-z0-9._-` |
| `NO_SOURCE` / `NO_SINK` | critical | fewer than one source or sink |
| `UNKNOWN_DOWNSTREAM` | critical | a downstream id is not in the plant |
| `SELF_LOOP` / `CYCLE` | critical | the flow graph has a cycle |
| `SOURCE_HAS_UPSTREAM` | critical | something flows into a source |
| `SINK_HAS_DOWNSTREAM` | critical | a sink has downstream |
| `DEAD_END` | critical | a non-sink asset has no downstream |
| `UNREACHABLE` | critical | asset not reachable from any source |
| `NO_SINK_REACHABLE` | critical | asset has no path to a sink |
| `MISSING_PARAM` / `BAD_PARAM` | critical | a required parameter is absent or out of range for the kind (see `docs/V1-Spec.md` §2 and `ParamValidator` in `TwinLabs.Simulation`) |
| `UNKNOWN_REF` | critical | a sensor `assetId`, `lineId`, `resourceId` or `shiftId` points at nothing |
| `RESOURCE_KIND` | critical | `resourceId` on a source, conveyor, buffer or sink |
| `BAD_RESOURCE_COUNT` | critical | resource count < 1 |
| `BAD_SHIFT` | critical | shift hours outside 0..24, or start = end |
| `BINDING_*` | critical | each message from `BindingResolver.Validate`, prefixed `BINDING_` |
| `OVERLAP` | warning | two asset footprints overlap |
| `LIMIT_ORDER` | warning | a sensor has `hiHi` ≤ `hi` |
| `NO_SENSORS` | warning | a machine, robot or inspection asset has no sensors |
| `MESH_URL` | warning | `mesh` does not start with `/api/meshes/` |

## 4. REST added in v0.3
| Method | Path | Body | Returns |
|---|---|---|---|
| POST | `/api/plant/validate` | `PlantModel` | `ValidationResult` (always 200) |
| PUT | `/api/plant` | `PlantModel` | `SnapshotData` (200). 422 problem+json with an `issues` array when critical issues exist. The sim resets to t=0 and keeps its run state; every WS client gets a `snapshot`. |
| GET | `/api/templates` | none | `TemplateInfo[]` |
| GET | `/api/templates/{id}` | none | `PlantModel` |
| GET / POST | `/api/layouts` | `SaveLayoutRequest` (POST) | `LayoutSummary[]` / `Layout` (201) |
| GET / PUT / DELETE | `/api/layouts/{id}` | `SaveLayoutRequest` (PUT) | `Layout` / `Layout` / 204 |
| GET | `/api/meshes` | none | `MeshInfo[]` |
| POST | `/api/meshes?name=cnc.glb` | raw body, `model/gltf-binary` or `model/gltf+json`, ≤ 20 MB | `MeshInfo` (201). 400 if the file doesn't start with the `glTF` magic (GLB) or `{` (glTF JSON). |
| GET | `/api/meshes/{id}/file` | none | the file, with its content type |
| DELETE | `/api/meshes/{id}` | none | 204 |

Templates live in `contracts/plant/templates/<id>.json` (id = file-name stem). `description` and `tags` come from a sibling `<id>.meta.json` (`{"description":"…","tags":[…]}`). The API links the folder into its build output as `plant/templates/`.

## 5. Templates (3 required)
| Id | Content |
|---|---|
| `machining-cell` | Source → conveyor → 2 CNC → buffer → robot → inspection → pack → sink, with 1 operator resource shared by the CNCs. About 10 assets. |
| `assembly-line` | Source → feeder → 3 assembly stations in series with buffers → test → pack → sink, with a day shift. About 12 assets. |
| `battery-cell-line` | Electrode coating → drying → calendering → slitting → stacking/winding → cell assembly → electrolyte fill → formation → ageing → grading → pack. Uses only the existing asset kinds with realistic params (formation and ageing as long-cycle machines behind buffers) and a formation-capacity resource. About 14 assets. |

Each template has realistic sensors with limits, `lineId`s, spacing along X with no footprint overlap, and must run for 8 sim hours producing good parts with line OEE between 0.3 and 0.9.

## 6. Plant Builder UI
Opens from the toolbar and from File → Plant Builder. It is a **2D plan view** (canvas, metres, 1 m grid, pan/zoom, snap-to-grid) built like a classic designer:
- **Palette** with the 7 asset kinds, creating sensible defaults (params, standard sensors with limits, size, an id like `CNC-03`).
- **Select / move / rotate / delete**, marquee select, copy/paste, undo/redo (Ctrl+Z / Ctrl+Y).
- **Connect tool:** drag from an asset to another to add a downstream; arrows show flow; click an arrow to remove it.
- **Property grid** for the selected asset: id, name, kind, position, rotation, size, line, resource, shift, mesh, params (with validation hints) and its sensors (add/remove/edit limits).
- **Plant properties:** name, seed, and editors for lines, resources and shifts (calendar).
- **Validation panel** listing `ValidationIssue`s live (debounced `POST /api/plant/validate`); clicking an issue selects the asset.
- **Apply to server** (`PUT /api/plant`), **New**, **Open template…**, **Save layout / Open layout…**, **Import / Export JSON**.
