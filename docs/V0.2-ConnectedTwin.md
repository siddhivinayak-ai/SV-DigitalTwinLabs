# v0.2 Specification — Connected Twin

## 1. Goal
Let the twin **mirror a real or emulated line** through industrial protocols, while keeping the simulator for prediction and what-if analysis.

| Mode | Who drives the asset and sensor state | Engine role |
|---|---|---|
| `simulate` (v0.1 behaviour) | The engine | Source of truth |
| `shadow` | External tags (OPC UA / MQTT) | Runs in parallel as a **predictor**. When prediction and reality diverge, it raises `deviation` alarms. |

Clients (web, Unity) do not change. They keep receiving the same `snapshot`/`tick`/`kpi` frames, whichever side produces the state.

## 2. Plant model additions (all optional, so v0.1 plants stay valid)
```jsonc
{
  "connections": [
    { "id": "plc1",   "kind": "opcua", "endpoint": "opc.tcp://localhost:4840/twinlabs", "publishingIntervalMs": 250 },
    { "id": "broker", "kind": "mqtt",  "endpoint": "mqtt://localhost:1883", "clientId": "twinlabs" }
  ],
  "bindings": [
    { "target": "sensor:CNC-01.temp",  "connectionId": "plc1",   "address": "ns=2;s=LineA.CNC-01.Temp" },
    { "target": "sensor:CNC-01.vib",   "connectionId": "broker", "address": "lineA/CNC-01/vib", "jsonPath": "$.value" },
    { "target": "asset:CNC-01.state",  "connectionId": "plc1",   "address": "ns=2;s=LineA.CNC-01.State",
      "stateMap": { "0": "off", "1": "idle", "2": "running", "3": "starved", "4": "blocked", "5": "fault", "6": "maintenance" } },
    { "target": "asset:SNK-01.good",   "connectionId": "plc1",   "address": "ns=2;s=LineA.SNK-01.Good" }
  ]
}
```
- `target` is either `sensor:<sensorId>`, or `asset:<assetId>.<state|good|scrap|wip|load|wear>`.
- `scale` and `offset` are optional: value = raw × scale + offset.
- `stateMap` maps the raw value as a string to an `AssetStateKind`.
- `jsonPath` is used for MQTT JSON payloads. Only the `$.field` / `$.a.b` subset is supported. With no `jsonPath`, the payload is parsed as a plain number.

## 3. Virtual PLC (built-in OPC UA server)
- Exposes the **simulated** line as OPC UA variables, so learners have a realistic endpoint to connect to, and shadow mode can be tested end to end with no hardware.
- Endpoint `opc.tcp://localhost:4840/twinlabs`, with anonymous access and `None` security in dev. Config: `Twin:VirtualPlc:Enabled`, `Port`.
- Address space: `Objects/TwinLabs/<LineId>/<AssetId>/{State (Int32 per the stateMap above), Good, Scrap, Wip, Load, Wear, <sensor suffix>...}`.
- Node ids are `ns=2;s=<LineId>.<AssetId>.<Name>`, for example `ns=2;s=LineA.CNC-01.Temp`. The suffix-to-name mapping is: temp→Temp, vib→Vib, power→Power, current→Current, speed→Speed, level→Level, rejects→Rejects, good→Good.
- The values are written from the sim each sim second. The server also exposes Methods `Start`, `Pause` and `InjectFault(assetId)`.
- `contracts/plant/sample_line.connected.json` = the sample line plus bindings that point at the virtual PLC. Shadow mode against the virtual PLC must therefore reproduce the simulated line.

## 4. Contract additions
- `SimStatus.mode`: `"simulate" | "shadow"`. It is new and always present from v0.2. Clients must ignore unknown fields.
- New WS message `connection`, sent on any change and in the snapshot as `connections[]`:
  ```json
  { "id": "plc1", "kind": "opcua", "endpoint": "opc.tcp://…", "status": "connected", "boundTags": 42, "lastValueMs": 761300, "error": null }
  ```
  `status` is one of `disabled`, `connecting`, `connected`, `error`.
- New alarm source `deviation`, raised in shadow mode when |predicted − actual| > max(3σ, 10% of the value) for 10 samples. Its id is `ALM-{sensorId}-deviation`.
- REST:
  - `GET /api/connections` → `ConnectionStatus[]`
  - `POST /api/twin/mode` `{ "mode": "shadow" }` → `SimStatus`. Returns 409 if shadow mode is requested with no bindings.
  - `POST /api/connections/{id}/reconnect`
- WS commands: `twin.mode` (value 0 = simulate, 1 = shadow).
